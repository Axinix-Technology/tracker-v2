Business Requirements Specification (BRS) AI-Powered Daily Work Status and Reporting System Natural-language work tracking A centralized workspace for daily updates, persistent tasks, follow-ups and evidence-based team reporting. Item Detail Backend Python + Django Frontend Flutter Database MySQL AI integration Configurable AI API Version 1.0 — Draft Type Standalone application, internal team use 1. Executive summary The AI-Powered Daily Work Status and Reporting System is an internal application designed to replace fragmented WhatsApp work-status messages and manually maintained Excel progress sheets with a centralized, searchable and structured work history. Employees currently describe their work in natural language, often mixing completed work, fixes, pending tasks, priorities, discussions and requests for additional information. This is convenient for communication but makes it difficult to determine precisely what was completed, when it was completed, which tasks remain open, who owns the next action and how an individual’s work has progressed over a selected period. The proposed system preserves the flexibility of natural communication while introducing reliable task tracking and reporting. Employees will be able to: Submit a free-text daily summary or communicate through an in-app chat interface. Describe work in their own words without learning a rigid reporting template. Review the AI’s interpretation and answer clarifying questions. Confirm or edit the structured work update before it is saved. See their own and their teammates’ work updates in a shared workspace. The system will use an AI API to interpret work updates and propose structured records. Django will validate and persist confirmed records in MySQL. Flutter will provide the conversational and reporting interface. Core business principle:  Employees should not have to think like a database or fill in repetitive forms. They should describe their work naturally, while the application handles organization, continuity, follow-ups and reporting. 2. Business problem and objectives 2.1 Current challenges Current method Business limitation WhatsApp status messages Updates are mixed with conversations and difficult to query systematically. Free-form daily summaries Different employees report different levels of detail. Excel progress sheets Employees must manually understand and maintain structured columns. Separate daily messages A task’s history and progress across multiple days are difficult to reconstruct. Informal pending-task mentions Ownership, priority, due dates and next actions may remain unclear. Manual management review Individual performance analysis requires reading messages and compiling data. 2.2 Business objectives Reduce the effort required to submit daily work status. Convert natural-language updates into consistent, structured records. Maintain continuity for tasks that remain open across multiple days. Distinguish completed work from ongoing work, blocked work and pending commitments. Enable team members to follow each other’s work in one shared location. Identify overdue follow-ups, missing information and unresolved high-priority work. Generate evidence-based reports for an employee or the entire team over a selected period. Preserve the source update and its history so AI interpretations remain traceable. Avoid unsupported performance ratings or conclusions that cannot be justified by recorded evidence. 2.3 Success criteria The application should be evaluated against measurable outcomes, including: Time required to submit a daily update. Percentage of updates successfully converted into useful structured records. Accuracy of task status, priority and completion-date extraction. Number of clarification rounds required per update. Percentage of pending tasks with an identified owner and next action. Time required to prepare an individual or team work report. User adoption and frequency of daily status submissions. Baseline measurements, target values and evaluation periods must be agreed before formal acceptance. 3. Product scope 3.1 In scope — Version 1 Secure login and internal team membership. Employee and manager access within one team. Natural-language daily status submission. Conversational AI clarification and draft generation. Free-text daily summary submission. Structured work-item extraction and employee confirmation. Persistent task records spanning multiple working days. Daily activity logs linked to persistent tasks. Task priorities, statuses, blockers and follow-up information. Shared team work feed and task search. Individual and team reports with date-range filters. Task history, edit history and traceability. AI-generated summaries grounded in stored records. Application settings for AI provider configuration and reporting preferences. Error handling, validation, audit history and operational monitoring. 3.2 Out of scope — Initial version WhatsApp API integration or automatic WhatsApp message importing. Integration with external project management, HRMS, ERP or ticketing systems. Automated employee performance ratings or rankings. Payroll, attendance, leave and employee productivity surveillance. Automatic task assignment based solely on AI inference. Automatic saving of AI-proposed updates without employee confirmation. External client or multi-organization tenancy. Automated task execution or code deployment. Generating performance conclusions from unrecorded work or private conversations. These exclusions may be considered in future releases following separate requirements approval. 4. Users, roles and permissions The application is initially intended for one internal team. Every team member can view the shared work updates, while record modification and administrative functions remain permission-controlled. Core business concepts The application must distinguish three related but different concepts. Daily Work Log What an employee reports doing on a particular day. A log preserves the day’s narrative and references the tasks mentioned in it. Example:  “Fixed the barcode rescanning issue and verified the quantity no longer increases.” Persistent Task A continuing unit of work with an owner, current status, priority and history. It may remain open over several days. Example:  “Resolve the remaining bill summary issues.” Task Activity / Progress Event A dated record of a change, milestone, progress update, blocker or completion event for a task. Example:  “On 21 October, completed the filter and stock movement column changes.” This separation is essential. If the same task is mentioned on five different days, the application should retain five dated progress events associated with one persistent task, rather than create five unrelated tasks or overwrite the earlier history. 6. Functional requirements The identifiers below should be used for development planning, test cases and acceptance tracking. 6.1 Authentication and team access FR-001:  The system shall authenticate internal team members. FR-002:  Each user shall have a unique account identifier and display name. FR-003:  The system shall maintain user roles and active/inactive status. FR-004:  All protected API operations shall validate authentication and permissions. FR-005:  All active team members shall be able to view shared work updates according to the agreed visibility rules. FR-006:  Each submitted update and task change shall be attributable to an authenticated user or an explicitly recorded system action. 6.2 Daily status submission FR-010:  Users shall be able to submit updates through an in-app conversational interface. FR-011:  Users shall also be able to paste or type a complete daily summary into a free-text input. FR-012:  The system shall accept natural language, numbered lists, headings and mixed completed/pending work descriptions. FR-013:  The original submitted text shall be preserved with its author and submission timestamp. FR-014:  Users shall be able to review and edit the AI-generated interpretation before confirmation. FR-015:  The system shall display the proposed work items in a readable format, not expose raw model output as the primary user interface. FR-016:  The user shall be able to cancel the draft without creating confirmed task records. FR-017:  The system shall prevent duplicate submissions caused by retries or repeated confirmation requests. 6.3 AI extraction and clarification FR-020:  The AI shall identify individual work items within a submitted summary. FR-021:  The AI shall distinguish completed work, in-progress work, pending work, blocked work and unresolved commitments when the source provides sufficient evidence. FR-022:  The AI shall extract explicit priorities, task owners, dates, blockers, dependencies and next actions where available. FR-023:  Missing required information shall trigger targeted clarification questions when the answer is necessary to create a reliable record. FR-024:  The system shall allow the employee to correct AI-generated fields. FR-025:  The system shall not invent completion claims, deadlines, ownership, priority or task descriptions. FR-026:  Ambiguous task matches shall be shown to the user for selection instead of silently linking unrelated tasks. FR-027:  The system shall distinguish an explicit statement from an inference or an unresolved field. FR-028:  The system shall support multiple clarification turns within the same draft session. FR-029:  The system shall show a final review screen before committing the confirmed update. 6.4 Task and progress management FR-030:  The system shall maintain persistent task records independently of individual daily logs. FR-031:  A task shall have a unique identifier, title, description, status, creation timestamp and change history. FR-032:  The system shall support configurable task priorities, including High, Medium and Low. FR-033:  The system shall allow a task to receive progress updates on multiple dates. FR-034:  Confirmed task completion shall record a completion timestamp and the supporting activity. FR-035:  Pending work shall remain visible until its status is changed through a confirmed action. FR-036:  The system shall support blockers and next actions where applicable. FR-037:  Users shall be able to view the chronological history of a task. FR-038:  The system shall support linking one daily log to multiple tasks and one task to multiple daily logs. FR-039:  The system shall detect possible duplicates and propose linking to an existing task where appropriate. FR-040:  The system shall preserve previous values in the change history when a confirmed edit changes a task’s status, priority, ownership or other tracked fields. Open decision:  Task assignment, percentage-based progress, due-date enforcement, task reopening and deletion policies require explicit business decisions before implementation. 6.5 Team work feed FR-050:  The system shall provide a centralized feed of confirmed daily work updates. FR-051:  The feed shall identify the employee, reporting date, summary and associated work items. FR-052:  Users shall be able to filter the feed by employee and date range. FR-053:  Users shall be able to search task titles and relevant descriptions. FR-054:  The system shall visually distinguish completed work from pending, ongoing and blocked work. FR-055:  The system shall provide a direct route from a feed item to its task history. FR-056:  Unconfirmed drafts and private clarification conversations shall not appear as confirmed team work. 6.6 Reporting and analysis FR-060:  The system shall provide individual work reports for a selected date range. FR-061:  The system shall provide team work reports for a selected date range. FR-062:  Reports shall distinguish work completed during the selected period from tasks still open at the end of the period. FR-063:  Reports shall show completed tasks, ongoing tasks, pending work and recorded blockers. FR-064:  Reports shall display task priorities and completion dates where those values are available. FR-065:  The system shall identify overdue tasks only when a due date exists and the overdue rule has been configured. FR-066:  The system shall generate a narrative summary using stored records and preserve links to the underlying evidence. FR-067:  Users shall be able to open the source task and daily log behind a report item. FR-068:  The system shall not interpret the number of tasks alone as proof of employee performance or quality. FR-069:  The system shall indicate when report data is incomplete or when important fields are unknown. FR-070:  Reports shall use a consistent, documented date-range convention and timezone. Scope decision:  Export to CSV, Excel or PDF is recommended but remains a scope decision for the first release. 6.7 Administration and configuration FR-080:  Administrators shall be able to manage user accounts and roles. FR-081:  Administrators shall be able to configure the supported AI provider, model and required API credentials. FR-082:  API credentials shall be stored securely on the server and never embedded in the Flutter application. FR-083:  The system shall provide configurable options for priorities and permitted task statuses. FR-084:  Administrators shall be able to inspect integration errors and application processing failures without exposing sensitive credentials. FR-085:  The system shall record audit events for important user and administrative actions. 7. AI behavior specification The AI is the natural-language interpretation layer, not the authoritative database or a replacement for business rules. 7.1 Required processing workflow Step Stage Description 1 Employee submits text Chat message or daily summary 2 AI extracts work items Actions, outcomes, task references, priorities, blockers and pending work 3 Validate and clarify Check required fields, ambiguity and existing task matches 4 Employee reviews draft Correct, add details, confirm task links or cancel 5 Django commits confirmed data Save daily log, task changes and audit history transactionally 6 Feed and reports update New records become searchable and available to authorized reports 7.2 AI extraction schema The AI should return structured data matching a server-defined schema. A proposed logical representation is shown below. {   "reporting_date": "2026-10-21",   "summary": "Completed high-priority stock and POS fixes.",   "work_items": [     {       "title": "Update sellable stock columns",       "work_type": "enhancement",       "status": "completed",       "priority": null,       "owner": null,       "due_date": null,       "outcome": "Changed the column structure for available sellable                   stock and stock in/out movement",       "blocker": null,       "next_action": null,       "existing_task_match": null,       "missing_fields": []     }   ],   "clarification_questions": [],   "warnings": [] } This is an illustrative schema, not a requirement that the model output exactly these values. The backend must validate the output against a versioned schema and reject invalid or unsupported values. Design requirements: Use enumerated values for status and work type. Use null for unknown fields rather than inventing values. Keep the original text associated with extracted work items. Distinguish task priority from task status. Represent task references explicitly. Store AI model and schema versions for traceability where practical. Never treat a model-generated identifier as a trusted database ID without server validation. 7.3 Clarification rules AI should ask questions when missing information materially affects task identity, status, ownership or the next action. Employee’s message Expected AI behavior “Fixed the barcode quantity issue.” Propose a completed fix; ask for additional detail only if needed by the required reporting format. “Bill summary needs to be completed.” Mark as pending or unresolved; ask who owns it or when it is due only if those fields are required by the agreed business rules. “Completed the high-priority items.” Ask which items if they cannot be reliably matched to the existing task list. “The report is nearly done.” Propose in-progress status; do not mark completed. “We discussed the remaining issues yesterday.” Preserve the discussion as context; do not infer that the issues were completed. “Added the stock filter.” Record the enhancement and reported outcome; do not invent a due date or priority. Important:  Not every missing field should block a submission. Otherwise, the AI will recreate the same rigid reporting burden the product is meant to eliminate. The business must define which fields are mandatory for a confirmed task and which may remain unknown. 7.4 AI safety and accuracy rules No invented facts:  Missing dates, owners, deadlines or outcomes must remain unknown.
